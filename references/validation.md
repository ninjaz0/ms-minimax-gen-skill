# 验收一次真实生成

一次验收要能回答：用的是哪个模型、输入怎样进入了工作流、哪些节点实际计算过、生成了哪个文件、文件能否完整播放。

## 按阶段收集证据

| 阶段 | 检查方法 | 可交付的证据 |
| --- | --- | --- |
| 模型 | `scripts/models.py MODE --action verify`，读取固定 revision 和摘要 | 每个组件的大小和 SHA-256 均匹配 |
| 服务 | `/system_stats` 和两个 `/object_info/<节点名>` | 进程使用预期输出目录，能在 ROCm 卡上找到 H3 原生节点 |
| 提交 | 查看 `state/jobs/<run-id>/api.json`、`submission.json`、`references.json` | 可复核的图、`prompt_id`、实际上传顺序及文件摘要 |
| 采样 | 查看 `history.json` 中的完成状态、`execution_cached` 事件和服务日志 | `sampler_cached: false`；成功历史中有本次 SaveVideo 输出 |
| 媒体验收 | 运行器用 PyAV 完整解码 MP4 | `validation.json` 保存帧数、尺寸、帧率、编码、时长、音轨参数、内容摘要和首帧 |
| 浏览器 | 在对应 Notebook 提交任务、等待自动出现播放器，实际播放 | 页面显示图像及时间进度，下载文件与服务端输出的 SHA-256 相同 |

T2V 验收应在图中看到 FL2VA 权重、纯文字输入和空的关键帧输入。R2V 应看到 Ref2VA 权重和 `LoadImage → ref_images.ref_image_0`，多图按上传顺序继续编号。图中保存的是 `/upload/image` 返回的实际文件名。同名上传、不同图片和含空格文件名都应保持正确关联。

两个工作流都用 24fps。5、10、15 秒预设分别生成 124、243、362 帧，符合 `17k+5` 帧网格。5 秒档的正常时长约为 5.17 秒。480p 预览为 864×480，768p 为 1344×768。

## 如何解释检查结果

- `validation.json` 会校验请求的帧数、尺寸、24fps、H.264，以及 32kHz 双声道 AAC。再核对 `duration_seconds` 是否与 `frames / fps` 相符。音频 RMS 可发现空音轨；故意静音的提示词可产生很低的数值。
- `sampled_frame_difference` 比较首、中、末帧的小图。镜头静止时数值也可能小。查看这些帧，判断动作、人物或主体外观与提示词是否一致。参考图验收要并排查看原图。
- `first-frame.png` 是从这次成片解码得到的首帧，可直接作为 R2V 示例输入。用浏览器的文件选择器上传亲自核对过的文件，检查图片编号或文件名，再提交。
- 新输出文件名只改变保存节点。重复提交同一提示词、参考图和种子时，采样可能复用缓存。若 `sampler_cached` 为真，可记录为 UI 提交与封装验证。测推理耗时要用新种子，且分别注明冷加载和排队时间。
- `seconds_to_observation` 从本次提交计至客户端读到完成历史。断线后很晚才执行 `resume` 会放大该数值，服务日志更适合分析纯计算时间。

需要独立复核时，在具有 FFmpeg 的机器上运行：

```bash
ffprobe -v error -show_entries stream=codec_type,codec_name,width,height,r_frame_rate,sample_rate,channels:format=duration,size -of json result.mp4
ffmpeg -v error -i result.mp4 -f null -
sha256sum result.mp4
```

macOS 可用 `shasum -a 256 result.mp4`。如试听、网页预览或多图模式尚未测试，交付时分别注明。

## 原实例的实测记录

下表来自原始部署和一次临时盘重建后的运行记录，均为单卡 AMD 环境、124 帧、20 步标准模式。它们给出估算排队和剩余时长的参照。

| 场景 | 分辨率 | 实测耗时 | 验证范围 |
| --- | --- | ---: | --- |
| 首次 T2V | 1344×768 | 约 12 分 40 秒 | 模型冷加载、生成、音视频解码、工作台预览 |
| 单图 R2V | 864×480 | 约 4 分 11 秒 | 参考主体与运动抽帧检查、音视频解码、网页上传与提交检查 |
| 重建后 T2V | 864×480 | 约 4 分 10 秒 | 新种子采样、124 帧完整解码、有声轨 |
| 重建后 R2V | 864×480 | 约 4 分 11 秒 | 输入文件摘要、新种子采样、124 帧完整解码、有声轨 |

原部署还确认了两个 Notebook 可在恢复的内核中生成交互控件。重建当次的浏览器最终页面复核超时。长时长、九图组合和 768p R2V 没有在这组实测中逐项验收。

公开版沿用上述原生节点连接和权重版本，并重新组织了源码获取、缓存目录、任务记录和 Notebook 入口。公开版发布前的离线检查覆盖两套图与原记录的对照、真实 MP4 解码、上传回执映射、任务提交和恢复查询。部署到新实例后仍应运行相应的 GPU 验收。
