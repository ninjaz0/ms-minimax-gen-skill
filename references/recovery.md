# 恢复、诊断与清理

## 先定位故障发生在哪一层

```bash
pwd
df -h /mnt/workspace /opt
python -c 'import torch; print(torch.__version__, torch.version.hip, torch.cuda.is_available())'
ls -ld state/ComfyUI /opt/ms-minimax-h3/venv /opt/ms-minimax-h3/models
curl -fsS --max-time 5 http://127.0.0.1:8188/system_stats
```

按实际部署修改目录和端口。Code Editor 显示“实例运行中”时，模型服务仍可能尚未启动。编辑器文件树提示无法监视文件变化时，执行“刷新资源管理器”，再与实例终端的目录结果核对。

| 观察 | 下一步 |
| --- | --- |
| Notebook、脚本、历史 MP4 在，临时盘 venv 或权重消失 | 记录缺失文件和恢复量，确认本次用途后运行 `bash scripts/restore.sh both` 或相应单模式。恢复后换新种子验收 |
| 文件大小或摘要不符 | 保留证据，将具体损坏文件移到同一临时盘的隔离位置；核对 SDK 对该文件的缓存状态，再重试固定 revision。检查可用空间 |
| `torch.version.hip` 为 None 或没有可见设备 | 在实例终端检查镜像和 `H3_PYTHON`。比较系统 Python 与 venv 的 torch 路径和版本。修复错误 venv 前先验证正确的基础解释器 |
| GitHub 访问失败 | 检查域名连通性与完整提交号，可经可信机器搬运固定提交的 Git bundle。保留工作区原有 checkout |
| 端口已被占用 | 查看 `/system_stats` 的 argv、源码、输出目录及 `/queue`。已运行其他项目时选另一个本地端口，不终止别人的进程 |
| 原生节点或模型下拉列表缺失 | 检查源码提交、`state/logs/comfy.log`、模型配置中目录名和当前模式。R2V 使用 `ref2va` 文件；T2V 使用 `fl2va` 文件 |
| 排队后断线或超时 | 保存任务目录与 `prompt_id`。查询 `/queue`、`/history/<prompt_id>` 和服务日志。用 `python scripts/generate.py resume <run-id>` 接回已有任务 |
| POST 超时且 ticket 尚未写入 | 保留 `state/jobs/<run-id>/api.json`。先按 `client_id`、输出前缀和队列/历史核对服务端是否已接受，再决定能否重提 |
| 服务/实例重启导致历史丢失 | 在 `state/outputs/h3` 找同一 run-id 的成片，并独立解码。没有成功记录也没有完整 MP4 时才重新生成 |
| 显存不足或实例即将到时 | 查看队列及实际显存，先缩短到 5 秒、使用 480p 和单张参考图。需要继续跑更昂贵配置时重新估时 |

恢复程序可再次执行。它会检查已有源码与文件摘要，继续补齐缺失组件。若 `git fetch` 中断，残留的 `state/ComfyUI.new.*` 是暂存目录，完成检查后只处理这一次失败产生的目录。多个 Agent 共用同一缓存时使用脚本的 `flock`，避免交叉写入。

## 复用老工作区

先盘点顶层，再查看选定项目中的 `restore*.sh`、`start*.sh`、Notebook 单元、权重清单和最近一次成功报告。旧安装可能通过两个软链接共同指向另一个顶层目录中的 ComfyUI，后者的 `models` 又指向临时盘。可用 `readlink -f`、`test -e` 及 `git -C <source> rev-parse HEAD` 逐层追踪。

保留依赖该源码的历史入口时，使用那份部署的启动/恢复命令及其配套清单。若迁移至本仓库的布局，要同时核对 Python 路径、输入目录、输出目录、权重搜索路径、内核和服务端口。用旧验收图作逐节点对照，再生成新视频验证。

## 网页有界面，按钮没有反应

1. 查看内核是否已连接。新建实例后，已有 Notebook 可能仍引用旧远程会话。选择显示实际临时盘 venv 路径的 Python 环境，再点“全部运行”重建控件。
2. 若只显示全局 Python，在命令面板选 `Python: Select Interpreter` → `Enter interpreter path...`，填实际 `venv/bin/python`。回到 Notebook 的内核选择器，选 `Python Environments...` 中同一路径。新版界面可能标成 `venv (Python 3.12.x)`。
3. 若只看得到 Notebook 工具栏，检查下方终端或“问题”面板是否最大化，先收起面板。若只显示 `VBox(...)`，检查 widgets 渲染器及内核的 `ipywidgets` 安装，重新运行界面单元格。
4. 浏览器自动化要定位当前真实标签和嵌套的 Notebook 输出区域，分别确认上传计数、生成状态和最终播放器。控件索引会随标签切换变化，使用当前页面可见的语义定位。文件选择事件超时但原生选择器已打开时，核对准确文件后完成原生选择。
5. 页面断开时，先查实例端队列与任务历史。浏览器重连不代表 GPU 作业失败。工作台等待生成期间应保持内核运行。需要继续使用终端时可按任务目录恢复查询。

## 清理无关项目

仅当用户要求清理时执行。先记录工作区顶层目录、大小、软链接目标、启动脚本硬编码路径以及在运行的作业。备份、训练数据、用户上传和平台隐藏配置分别识别。历史项目目录名含“H3”或“Qwen”都不足以单独判断归属。

制作具体的保留/清理清单，保留两套入口、共享源码、虚拟环境和权重的实际位置、模型清单、输入及结果。需要回收时先验证此挂载点支持回收和恢复，把本批项目移入回收站并逐项核对。回收站若与工作区同盘，仍会占用配额。

永久删除前让用户看到具体范围、容量和不可恢复的后果。仅处理获确认的这一批，同时验证目标原路径和回收条目的对应关系。完成后刷新文件树，再次核对共享链接、内核、GPU、六个组件和两个真实生成任务。保留删除前占用与删除结果，避免将共享文件系统的 `df` 变化当作个人配额变化。
